---
title: "Design: Kimi-Linear PD Disaggregation with Decode Context Parallelism"
---

Status: Implemented and validated on 8xB200

## Summary

Add a supported single-node deployment for `moonshotai/Kimi-Linear-48B-A3B-Instruct`
with:

- prefill on GPUs 0-3 using TP=4 and, after the correctness baseline, EP=4;
- decode on GPUs 4-7 using TP=4 and DCP=4;
- `tokenspeed_mla`, FP8 KV cache, and the `a2a` DCP reduction on decode;
- Mooncake and NIXL transfer backends;
- GSM8K, deterministic output/logprob parity, and CUDA graph/eager decode gates.

In this document, "TEP=4" means TP=4 with EP=4 colocated on the same four
prefill GPUs. SGLang does not have a `--tep-size` option. Development first
isolated cache correctness with EP disabled; the registered acceptance profile
uses `--ep-size 4`.

The host targeted by this work has eight B200 GPUs. The initial implementation
is therefore single-node and uses one four-GPU process group per PD role.

## Motivation

Kimi-Linear is a hybrid model:

- MLA full-attention layers store token-indexed latent KV;
- KDA linear-attention layers store request-indexed recurrent state;
- routed MoE layers can use expert parallelism independently of cache transfer.

SGLang already supports these pieces separately:

- monolithic Kimi-Linear TP=4 + DCP=4 with TokenSpeed MLA;
- PD transfer of hybrid MLA KV and KDA/Mamba state;
- heterogeneous attention-TP rank mapping;
- GSM8K acceptance coverage for both Kimi-Linear and PD deployments.

The missing composition is PD transfer into a DCP-striped decode cache. The
disaggregation stack currently exchanges attention-TP, CP, DP, and PP topology
but has no DCP metadata or DCP-specific transfer layout. A dense prefill cache
cannot be copied page-for-page into decode storage whose owner rule is
`position % dcp_size == dcp_rank`.

## Goals

1. Correctly transfer Kimi-Linear MLA KV from a non-DCP prefill worker into a
   DCP=4 decode worker.
2. Preserve the existing one-to-one KDA recurrent-state transfer when prefill
   and decode both use TP=4.
3. Keep all DCP=1 and non-Kimi PD paths byte-for-byte on their existing fast
   path.
4. Make the supported topology explicit and fail early for unsupported
   combinations.
5. Add a registered 8xB200 end-to-end test that matches the observed
   monolithic TP4+DCP4 GSM8K baseline within sampling noise.
6. Add finer correctness checks that can detect cache-layout corruption even
   when aggregate GSM8K accuracy is noisy.

## Non-goals

- DCP for KDA computation. KDA remains tensor-parallel; DCP accelerates and
  expands the cache capacity of the MLA layers only.
- Heterogeneous prefill/decode TP in the first milestone.
- Decode-side radix cache, ReplaySSM, speculative decoding, or multi-node DCP
  in the first milestone.
- The non-MLA GPU staging-buffer path. Kimi-Linear uses hybrid MLA storage and
  must not use that staging path.
- Changing the DCP attention kernels or owner rule.

## Existing architecture

### Prefill role

The prefill scheduler computes all prompt tokens, stores dense MLA KV in
`HybridLinearKVPool.full_kv_pool`, and stores the final KDA state in its Mamba
pool. The PD sender obtains:

- MLA page indices from `req_to_token`;
- one Mamba slot index for the recurrent state;
- destination registration and index metadata from the decode worker.

### Decode role

The decode scheduler preallocates cache space, sends destination metadata to
prefill, waits for transfer completion, then builds a prebuilt extend batch that
skips prompt recomputation.

With DCP enabled, the allocator uses a virtual page size of
`physical_page_size * dcp_size`. Token ownership is striped by logical position,
while each DCP rank's attention kernel consumes a packed local view.

### Current mismatch

PD metadata contains attention-TP information but no DCP size or rank. Existing
KV transfer paths pair source and destination pages and copy contiguous page
rows. For DCP=4:

- one virtual decode page represents four physical local pages worth of logical
  positions;
- each decode rank owns every fourth logical token;
- the owned source rows are strided in the prefill cache;
- the destination rows are packed in rank-local order.

Contiguous page copying therefore cannot express the required mapping.

KDA state is different: it is sharded by TP, not by DCP. With TP=4 on both
sides, the existing corresponding-rank state copy is the desired behavior.

## Implemented design

### 1. Advertise DCP topology

Destination registration metadata now carries:

- `dcp_size`;
- `dcp_rank`.

The bootstrap capability is negotiated through `pd_wire_version`. New decoders
reject DCP transfer when prefill does not advertise striped-transfer support,
while old decoders receive the legacy JSON schema without unknown fields.
Registration continues to reject physical page-size and KV-dtype mismatches.
The existing `KVArgs.page_size` remains the physical page size; DCP scaling
applies only to the virtual allocator.

The topology resolver will support this first matrix:

- prefill `dcp_size == 1`;
- decode `dcp_size` in `{1, 4}`;
- equal prefill/decode attention TP;
- decode attention CP=1;
- Kimi-Linear hybrid MLA pool;
- Mooncake, then NIXL.

Other PD+DCP combinations fail at bootstrap with a descriptive error instead of
silently copying an incompatible layout.

### 2. Build a backend-independent DCP transfer plan

`build_dcp_token_transfer_plan` is a pure NumPy helper in
`disaggregation/common/utils.py`. Its inputs are:

- ordered source physical page IDs for the transferred prompt range;
- ordered destination physical page IDs;
- source page offset within the complete transfer delta;
- aligned decode prefix length;
- exact number of valid logical tokens in the chunk;
- physical page size;
- destination DCP size and rank.

For each logical position `p`, destination rank `r` owns the token when:

```text
p % dcp_size == r
```

The corresponding rank-local row is packed by logical ownership:

```text
dst_local = relative_position / dcp_size
dst_physical = dst_page[dst_local / page_size] * page_size
             + dst_local % page_size
```

The plan emits coalesced `(source address, destination address, byte length)`
segments. Coalescing is allowed only when both source and destination rows are
contiguous. The exact token count prevents copying stale rows from a final
partial source page. This makes partial pages, page-aligned prefixes, chunked
prefill, and arbitrary allocator page IDs explicit instead of relying on
page-level `zip`.

The helper is independent of Mooncake/NIXL and is unit-testable without GPUs or
transfer libraries.

### 3. Add an ownership-aware MLA transfer path

When destination DCP is greater than one and the pool is MLA or hybrid MLA:

1. Decode sends destination physical page IDs plus DCP topology for the
   transfer range.
2. Prefill filters by logical prompt position, not by source cache index modulo.
3. Prefill converts source and destination token locations into the transfer
   plan.
4. Each destination DCP rank receives only its owned token rows.
5. Existing MLA layer/PP pointer selection is reused.

The DCP=1 path remains unchanged. KDA/Mamba state metadata remains separate and
continues through the existing state-transfer path.

Mooncake emits explicit address/length blocks. NIXL uses non-prepared,
token-row descriptors because its existing prepared descriptors are
page-granular. Both consume the same transfer plan. No staging buffer is
enabled for this equal-TP path.

### 4. Preserve KDA state semantics

KDA state follows attention TP rather than DCP. For the supported TP4-to-TP4
topology:

- prefill TP rank `i` sends its recurrent-state shard to decode TP rank `i`;
- exactly one request-state slot is transferred;
- no DCP filtering or replication is applied;
- state dimensions and item lengths must match at bootstrap.

Unit and end-to-end tests will assert this invariant. Future heterogeneous TP
support can continue to use the existing state-slicing helper, but it is outside
the first milestone.

### 5. Validate CLI combinations

Add explicit PD+DCP policy checks:

- reject DCP>1 on a PD prefill role;
- allow DCP>1 on a PD decode role only for a validated model/backend/layout;
- require `tp_size % dcp_size == 0`;
- initially require equal prefill/decode attention TP at bootstrap;
- require matching KV dtype and physical page size;
- reject ReplaySSM, decode radix cache, and the non-MLA staging buffer;
- log the resolved TP/EP/DCP topology and transfer layout once per worker.

These checks are role-aware. A monolithic Kimi-Linear DCP launch keeps its
existing behavior.

### 6. Add observability

Expose or log:

- DCP size/rank in decode worker/server information;
- number of logical prompt tokens and locally owned transferred tokens;
- transfer bytes for MLA KV and recurrent state separately;
- selected transfer layout (`dense` or `dcp_striped`);
- a counter for rejected incompatible bootstrap registrations.

For DCP=4, each decode rank should receive approximately one quarter of the
prompt's MLA KV rows, plus its full TP-local KDA state shard.

## Target launch profiles

### Correctness profile

Prefill, GPUs 0-3:

```bash
--disaggregation-mode prefill
--tp-size 4
--dcp-size 1
--attention-backend tokenspeed_mla
--kv-cache-dtype fp8_e4m3
--dtype bfloat16
--trust-remote-code
```

Decode, GPUs 4-7:

```bash
--disaggregation-mode decode
--base-gpu-id 4
--tp-size 4
--dcp-size 4
--attention-backend tokenspeed_mla
--kv-cache-dtype fp8_e4m3
--dcp-comm-backend a2a
--dcp-replicate-q-proj
--cuda-graph-max-bs-decode 64
--dtype bfloat16
--trust-remote-code
```

Both roles use the same transfer backend and physical page size.

### TEP prefill profile

The registered test adds `--ep-size 4` on prefill. EP does not change PD cache
layout, and the final TP4+EP4 acceptance run passed the same DCP transfer gates.

## Implementation status

### Phase 0: Prove the gap and lock baselines — complete

1. Run existing CPU DCP layout/config/model tests.
2. Run the existing monolithic Kimi-Linear DCP4 GSM8K test.
3. Add a temporary/manual homogeneous Kimi-Linear PD profile with DCP=1.
4. Run the target PD+DCP launch before changes and capture the first concrete
   failure or accuracy corruption.

This phase prevents implementing a speculative relayout against an unverified
failure mode.

### Phase 1: Pure layout and wire metadata — complete

1. Add DCP fields to bootstrap and destination registration metadata.
2. Add the pure DCP transfer planner.
3. Cover exact pages, partial pages, odd prompt lengths, nonzero prefixes,
   chunk boundaries, and randomized virtual page IDs in CPU tests.
4. Add backward-compatibility tests for peers with no DCP field.

### Phase 2: Mooncake implementation — complete

1. Add ownership-aware hybrid-MLA transfer using the shared plan.
2. Keep recurrent-state transfer on the existing path.
3. Add byte-count and mapping assertions in debug/test mode.
4. Verify homogeneous PD remains unchanged.

### Phase 3: End-to-end acceptance — complete

Add `test/registered/disaggregation/test_kimi_linear_pd_dcp4.py` using the
existing PD fixture and the live `nightly-8-gpu-b200` registration.

The test will cover:

- prefill/decode/router health;
- temperature-zero short generation;
- decode CUDA graph replay at batch size 2;
- eager decode above the graph limit at batch size 65;
- positive decode cache capacity;
- GSM8K: 200 examples, 5-shot, 4 threads, score at least 0.88. The observed
  deterministic monolithic TP4+DCP4 baseline on the same runner is 0.89.

Add a manual sequential parity test that compares aggregate or monolithic DCP
against PD+DCP for:

- exact generated token IDs at temperature zero;
- output logprobs within an established tolerance;
- prompts crossing physical and virtual page boundaries.

### Phase 4: TEP and NIXL — complete

1. Enable prefill EP=4 and rerun the same acceptance gates. (Complete)
2. Implement NIXL using the backend-independent transfer plan. (Complete)
3. Run Mooncake/NIXL smoke parity. (Complete; transfer-byte instrumentation is
   still a hardening item.)
4. Record TTFT, inter-token latency, and transfer throughput as non-blocking
   performance data.

### Phase 5: Hardening — pending

Add abort/cleanup, repeated prefix, concurrent transfer, and long-prompt cases.
Consider multi-node and heterogeneous TP only after the single-node matrix is
stable.

## Test matrix and acceptance criteria

The required merge gate is:

- all new CPU layout/wire tests pass;
- existing DCP config/layout/Kimi unit tests pass;
- existing TokenSpeed MLA DCP kernel tests pass;
- existing monolithic Kimi-Linear DCP4 smoke remains green (its 200-example
  GSM8K run scored 0.89 against a 0.90 threshold);
- homogeneous Kimi-Linear PD DCP=1 reaches its established GSM8K baseline;
- target TP4 prefill to TP4+DCP4 decode reaches GSM8K >= 0.88;
- batch 2 CUDA graph replay and batch 65 eager decode both complete;
- deterministic token/logprob parity shows no systematic divergence;
- existing non-DCP PD tests remain on the dense transfer path.

## Validation results

On the target 8xB200 host:

- monolithic TP4+DCP4 completed its smoke/capacity gates and scored 0.89 on the
  deterministic 200-example GSM8K slice;
- Mooncake prefill TP4+EP4 to decode TP4+DCP4 passed all three registered
  tests, including CUDA-graph batch 2, eager batch 65, and positive capacity;
- the post-hardening TEP4 Mooncake run scored 0.905 GSM8K with 36.50 seconds
  evaluation latency and 526.16 output tokens/second;
- the same TEP4 PD+DCP smoke passed with the NIXL UCX backend;
- after exact final-page token counts and capability negotiation were added,
  both Mooncake and NIXL smoke gates passed again;
- 93 focused CPU layout, wire, server-argument, NIXL, and existing Kimi DCP
  regression tests passed, plus five subtests.

## Risks and mitigations

### Silent cache corruption

GSM8K alone is too coarse. Add pure mapping tests and deterministic parity
before relying on the accuracy score.

### Prefix and page-boundary errors

Plan by logical prompt position and test nonzero decode prefixes, partial pages,
and chunked sends. Do not infer ownership from allocator page IDs.

### Excessive transfer fragmentation

Start with correct token-row segments, then coalesce adjacent source and
destination ranges. Track segment count and transfer bytes.

### KDA state duplication or omission

Keep state transfer outside DCP KV planning and assert one TP-local state copy
per destination rank.

### Scope expansion

Hold the first implementation to equal TP, DCP on decode only, no speculation,
and no decode radix cache. Add EP only after correctness.
